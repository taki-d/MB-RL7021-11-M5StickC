# 電力更新の長い空白の調査（2026-10-07）

## 7秒台の空白の再現

要求ごとに異なるTIDを付け、デバイスの `millis()` で送信開始、
`EVENT 21`（送信完了通知）、ECHONET Lite応答の受信を記録した。
認証情報やUARTの生データは診断ログに含めない。

電力単独の要求で7.704秒の更新間隔を再現した。デバイス時刻での内訳は以下。

| 事象 | デバイス時刻 ms | 前事象からの時間 |
| --- | ---: | ---: |
| 前の電力応答受信 | 409563 | — |
| 次のE7要求開始（TID 167） | 409601 | 38ms |
| 送信完了通知、status=00 | 409765 | 164ms |
| 同じTIDのE7応答受信 | 417268 | 7503ms |

この区間に電流・積算値の要求はない。したがって、この空白を
他メトリクスの割り込みだけで説明することはできない。
大半は送信完了通知後の応答待ちであり、メーター処理・返信経路側を
さらに調べる必要がある。電波再送とメーター内部処理のどちらかは、
このホスト側のログだけでは断定できない。

## 基準測定

最小要求間隔1秒、E7/E8別取得、電流30秒間隔で240秒間観測。
E7は92応答・92回の取り込み、E8は7応答、タイムアウトなし。
電力更新間隔は中央値2.400秒、95パーセンタイル4.800秒、最大7.704秒。
別々にE8→E7を要求した場合の約4.8秒の空白と、E7単独の返信遅延を区別できた。

## 電流ONでの比較試験と採用した設定

以下は電力サンプルの**受信間隔**。メーター内部の測定周期ではない。
観測時間・起動条件が異なるため、特に最大値を条件間の性能保証として扱わない。

| 条件 | 観測時間 | 電力サンプル数 | 中央値 | P95 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 基準：最小要求間隔1秒、E7/E8別取得 | 240秒 | 92 | 2.400秒 | 4.800秒 | 7.704秒 |
| 最小1秒、電流取得時にE7+E8を一括要求 | 240秒 | 96 | 2.400秒 | 4.404秒 | 4.505秒 |
| 最小3秒、E7/E8別取得（起動から） | 240秒 | 66 | 3.004秒 | 4.796秒 | 7.603秒 |
| 一括取得＋診断追加、起動時の順序修正前 | 180秒 | 61 | 2.400秒 | 4.508秒 | 5.508秒 |
| 最終版：起動時の順序も修正（起動から） | 100秒 | 27 | 2.400秒 | 4.507秒 | 8.504秒 |

3秒に緩めても7秒台の空白が再現し、通常時の更新は遅くなった。
そのため最小要求間隔は1秒に戻し、応答を受けてから次を送る方式を維持した。
これは1秒更新を保証する設定ではない。

電流取得時の典型的な空白は、別取得の約4.8秒から一括取得の約4.4秒へ短縮した。
改善幅は小さく、一括取得でも長い返信待ちは解消していない。
最終版のTID 18では以下を観測した。

| 事象 | デバイス時刻 ms |
| --- | ---: |
| 前の電力応答 | 59637 |
| E7+E8要求開始 | 59677 |
| 送信完了通知、status=00 | 59836 |
| 応答受信 | 68141 |

8.504秒の空白のうち、送信完了後の返信待ちは8.305秒。
この要求中のファームウェアの `loop()` 呼び出し間隔は最大45msだった。
したがって、この事例もファームウェアが数秒間停止した現象ではない。
単独取得・一括取得の両方で返信遅延が出ているが、原因が同一か、
一括取得が遅延の発生率に影響するかはこの標本数では判断できない。

最終版では、E1・E0・E3など遅い取得の次にはE7単独を優先する。
起動時にE1→E7+E8が続いていた5.5秒の空白については、
E1→E7単独の3.296秒に短縮できた。積算値の取得も電力を挟んで実行する。
電流は30秒、積算値は30分の要求間隔を維持した。

### 最終確認

- PlatformIOのビルド・実機書き込みに成功。
- 起動後100秒でE7単独24応答＋一括3応答＝電力27サンプル。取り込み漏れなし。
- 電流3回、単位・正方向積算・逆方向積算を各1回取得。
- タイムアウト・一括取得からのフォールバックは0回。終了時の1要求は計測終了時点の応答待ち。
- ホスト側プロトコルテスト、`git diff --check` に成功。
- 実機の `/metrics` で全メトリクスと診断値を確認し、`/healthz` は `200 ok`。
  通常の応答待ちも接続中として扱うため、連続取得だけを理由に不健康とは判定しない。

### 計測上の注意

3秒間隔の試験時だけ、収集スクリプトが新しい `loop_gap` フィールドの
アンダースコアを許可せず、応答行を集計できなかった。
上表は正常に採取できた電力値の受信時刻から算出している。
この試験の `responses_ms` と `inflight_at_end=77` は無効であり、
77要求が並列に残っていたという意味ではない。スクリプトは修正済み。

一括取得240秒試験の先頭応答は要求が採取開始前にあるため、
旧スクリプトではE7単独に分類されていた。要求不明の応答を
単独取得のRTT評価に使わない。現在は `request_not_captured` と区別している。

## 追加検証：電流取得をOFFにした比較

電流が不要という要望に合わせ、`kEnableInstantaneousCurrent = false` に変更して
実機へ書き込んだ。電力の最小要求間隔1秒、積算値の30分間隔、設置位置は変更していない。
`kCombinePowerAndCurrent` がtrueでも、電流OFF時にはE8を含む要求を送らない。
電流メトリクスの公開も停止する。検証後もこの設定を維持している。

変更前後をそれぞれ240秒採取した。OFF側は書き込み後の60秒を読み捨てたが、
最初のE7要求が60秒タイムアウトし、想定より初期取得の完了が遅れた。
このため定常状態の比較には、**両ログとも末尾180秒（`60 <= at < 240`）**を使った。
OFF側ではこの区間に入る前に単位・正方向積算・逆方向積算の初期取得が完了している。
起動時のタイムアウトを除去した成功率として扱うのではなく、下に別記する。

| 定常180秒の結果 | 電流ON（一括取得） | 電流OFF |
| --- | ---: | ---: |
| 電力サンプル数 | 71 | 77 |
| 受信間隔の平均 | 2.515秒 | 2.341秒 |
| 受信間隔の中央値 | 2.400秒 | 2.400秒 |
| 受信間隔のP95 | 4.404秒 | 2.404秒 |
| 受信間隔の最大 | 4.504秒 | 2.404秒 |
| 3秒超の受信間隔 | 6回 | 0回 |
| この区間内のタイムアウト | 0回 | 0回 |

ON側の6回の長い空白はE7+E8一括要求に対応した。
OFF側の要求はE7単独77件で、E8単独・一括要求とも0件。
デバイス時刻での最大受信間隔もON 4.507秒、OFF 2.406秒であり、
PC側のシリアル読み取り時刻だけによる差ではない。

**電流OFFは定期的な4秒台の待ちをなくす効果があったが、通常の2.4秒周期は変わらない。**
電力の応答自体が通常約2〜2.4秒かかっており、要求間隔の設定はすでに1秒なので、
この設定値をさらに短くしても今回の通常周期を短縮できる根拠はない。
応答を受け取るまで次の要求は送らない。

### 全採取区間と制約

- ONの240秒全体は電力95サンプル、P95 4.404秒、最大4.504秒、タイムアウト0回。
- OFFは60秒読み捨て後の240秒全体で電力91サンプル、P95 2.404秒、最大3.707秒。
  初期積算値の取得による3.496秒・3.707秒の空白を含む。
- OFFの最初のE7要求（TID 1）が起動約80.8秒の時点でタイムアウトし、
  その後は自動で取得を再開した。要求開始・送信完了は読み捨て区間内のため、
  この試行のログでは送信完了状況や未応答の原因までは確認できない。
  電流OFFがこのタイムアウトの原因かどうかも、この試行だけでは判断できない。
- 定常状態では7〜8秒台の空白は再現しなかったが、短時間の1回ずつの比較であり、
  まれな返信遅延が解消した保証にはならない。
- 積算値は有効のままなので、起動時と30分ごとの取得で電力更新間隔が延びる可能性は残る。
- ビルド・実機書き込み成功。`/metrics` で電流系列がないこと、電力と積算値が返ること、
  `/healthz` が正常なことを確認した。プロトコルテストと計測スクリプトの2テストも成功。

採取ログはローカルの一時ファイル（自動削除される可能性あり）:

- `/tmp/m5-current-on-ab-20261007.jsonl`
- `/tmp/m5-current-off-ab-20261007.jsonl`

再び電流が必要になった場合は `kEnableInstantaneousCurrent = true` に戻して
再ビルド・書き込みする。

## 診断値と今後の切り分け

`firmware/src/metrics_config.h` の既存の個別ON/OFFに加え、以下を追加した。

- `kCombinePowerAndCurrent`: 電流取得時のE7+E8一括要求。有効が既定。
  Get_SNA・不完全な応答・タイムアウト時は、その起動中は別取得へ戻る。
- `kEnablePowerTimingMetrics`: 以下の診断値を `/metrics` に公開する。
  電力取得自体が無効なら公開しない。

| メトリクス | 意味 |
| --- | --- |
| `instantaneous_power_samples_total` | 受信・取り込み済みサンプル数。同じW値も数える |
| `instantaneous_power_sample_age_seconds` | 最後の電力サンプル受信からの経過秒 |
| `instantaneous_power_sample_gap_seconds` | 直近2サンプルの受信間隔 |

これにより「電力値が同じ」と「返信が来ていない」を区別できる。
メーター内部の測定時刻は取得していないため、測定値そのものの鮮度とは異なる。
`sample_gap_seconds` は次の返信で上書きされるので、スクレイプが遅い場合は
長い空白を取りこぼす。詳細な切り分けにはシリアルのTID付きログを利用する。

残る長い返信待ちには、設置位置を変えたA/B比較が次の候補。
現位置とメーターに近い位置で同じ設定・同程度の時間を採取し、
送信完了後の待ち時間と長い空白の発生率を比較する。
一括取得ON/OFFも別条件として比較し、同時に複数の条件を変えない。
電波品質の問題とはまだ断定できず、位置で変わらなければメーター側処理や
返信経路を調べるための無線情報・ベンダー情報が必要になる。

## タイムアウトを短くして重ねて送信する案について

[ECHONETのAIF仕様書 1.10](https://echonet.jp/wp/wp-content/uploads/pdf/General/Standard/AIF/lvsm/lvsm_aif_ver1.10.pdf)
2.4.1〜2.4.4では、連続要求は応答受信後または所定のタイムアウト後とされる。
タイムアウトの下限は通常の単一プロパティが20秒、複数プロパティが60秒。
このため、2〜3秒で打ち切って要求を重ねる方式は今回採用しない。
7秒台の応答も同じTIDの有効な応答として処理する。
